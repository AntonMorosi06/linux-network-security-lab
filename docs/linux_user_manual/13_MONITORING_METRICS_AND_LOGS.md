# Monitoring, Metrics and Logs

This file explains monitoring, metrics and logs in depth for the Linux User Manual. Monitoring answers whether a system is alive, healthy and behaving as expected. Metrics provide numeric measurements over time. Logs provide event-level explanations. Together, they form the practical observability layer used throughout the Linux Network Security Lab.

The purpose of this file is to teach the difference between status endpoints, health checks, metrics endpoints, service logs, dashboard panels and alert rules. A service is not fully understandable just because it is running. It should be observable through commands, HTTP endpoints, logs, Prometheus-style metrics and, when useful, Grafana dashboards.


## 1. Observability concept

Observability is the ability to understand a system's internal state from its external outputs. In this repository, the main outputs are status endpoints, health endpoints, metrics endpoints, logs, dashboards and reports.


## 2. Monitoring versus logging

Monitoring tracks state and trends over time, while logging records discrete events. Both are needed. Metrics tell how often errors occur; logs explain what happened in individual cases.


## 3. Status endpoint

A status endpoint is a simple endpoint that tells whether a service is responding. It may return uptime, version or basic state.


## 4. Health endpoint

A health endpoint is usually more specific than status. It may check dependencies, internal readiness, configuration and whether the service should receive traffic.


## 5. Metrics endpoint

A metrics endpoint exposes numeric values, often in Prometheus text format. Metrics can include request counts, error counts, latency, uptime and current state.


## 6. Logs

Logs are event records. They include timestamps, messages, severity levels, status codes and contextual fields. Logs are useful for diagnosis and incident response.


## 7. Prometheus

Prometheus is a monitoring system that scrapes metrics from configured targets. It stores time series and allows queries using PromQL.


## 8. Prometheus scrape

A scrape is the act of Prometheus requesting metrics from a target. If scraping fails, Prometheus may mark the target as down.


## 9. Prometheus target

A target is an endpoint Prometheus scrapes. In local labs, targets should usually be localhost or internal Docker service names.


## 10. Prometheus query

A Prometheus query asks for metrics or expressions over metrics. The `up` metric is commonly used to check whether a target is reachable.


## 11. Prometheus text format

Prometheus text format uses metric names, optional labels and values. It may include HELP and TYPE comments.


## 12. Counter

A counter is a metric that increases over time, such as total requests or total errors. It is useful for rates and cumulative counts.


## 13. Gauge

A gauge is a metric that can go up or down, such as current active requests, memory usage or queue size.


## 14. Histogram

A histogram groups observations into buckets, often used for request latency. It can be more complex than counters and gauges.


## 15. Labels

Labels add dimensions to metrics. For example, a request metric may have labels for method, path or status code. Labels are powerful but high cardinality can be problematic.


## 16. Grafana

Grafana visualizes metrics through dashboards. It can connect to Prometheus and display panels, graphs, stat cards and alert states.


## 17. Dashboard

A dashboard is a visual collection of panels. It should answer operational questions quickly, not just look impressive.


## 18. Panel

A panel is one visualization inside a dashboard. Panels should have clear titles, units and queries.


## 19. Alert rule

An alert rule defines a condition that indicates a problem. Alerts should be meaningful and not too noisy.


## 20. Alert fatigue

Alert fatigue happens when alerts are too frequent or low-value. A useful alert should require attention or investigation.


## 21. Logs and metrics together

Metrics show trends; logs explain events. A spike in 500 errors should be investigated with logs from the same time window.


## 22. Correlation

Correlation means connecting metrics, logs and commands. For example, a curl 500 response, API error log and Prometheus error counter may describe the same event.


## 23. Synthetic metrics

Local labs may use synthetic metrics generated by a controlled API. This is safe for learning and avoids using private production data.


## 24. Service-level indicators

SLIs are measurable indicators such as availability, latency and error rate. They help define service behavior objectively.


## 25. Availability

Availability asks whether the service is reachable and functioning. In local labs, curl and Prometheus `up` can provide availability signals.


## 26. Error rate

Error rate measures the proportion or rate of failed requests. It is useful for detecting service degradation.


## 27. Latency

Latency measures how long requests take. It matters for performance and user experience, but may not be deeply implemented in every local lab.


## 28. Runbook

A runbook tells an operator what to check when an alert fires. Good monitoring should be connected to runbooks.


## 29. Local monitoring safety

Local monitoring should avoid exposing dashboards broadly. Bind Grafana and Prometheus to localhost where possible.


## 30. Publishing dashboards

Dashboard JSON can be committed if it contains no secrets or private endpoints. Screenshots should be reviewed before publication.


## 31. Monitoring report

A monitoring report should include target, metrics checked, query used, dashboard state, alert state and interpretation.


## 32. Repository connection

This repository uses monitoring in Prometheus metrics labs, Grafana dashboard labs, capstone services, SIEM-style pipelines and final review reports.


## Command card 1: `curl status`

### Purpose

Test service status endpoint.

### Example

```bash
curl -i http://127.0.0.1:8800/status
```

### Expected output

```text
HTTP status and body.
```

### Interpretation

This command supports observability. A strong interpretation should state what was measured or observed, whether the service was reachable, whether metrics/logs matched expectations and what conclusion follows.

Safe local check.

## Monitoring, metrics and logs reference tables

| Signal | Meaning | Example |
|---|---|---|
| Status | basic service response | `/status` |
| Health | readiness or dependency state | `/health` |
| Metrics | numeric time-series values | `/metrics` |
| Logs | event-level detail | API/proxy/container logs |
| Dashboard | visual metric summary | Grafana panels |
| Alert | condition requiring attention | error rate too high |

| Metric type | Behavior | Example |
|---|---|---|
| Counter | only increases | total requests |
| Gauge | can rise or fall | active requests |
| Histogram | bucketed observations | request duration |
| Summary | statistical summaries | quantiles |

| Problem | Metric clue | Log clue |
|---|---|---|
| service down | `up == 0` | connection refused or startup failure |
| auth failures | 401 counter increases | auth_failure events |
| missing route | 404 counter increases | not_found path logs |
| backend errors | 500 counter increases | stack trace or controlled error |
| proxy issue | target unavailable | 502/504 proxy logs |


## Monitoring study card 1: Observability

### Concept

A service should expose enough signals to understand its state.

### Practical check

```bash
curl -i http://127.0.0.1:8800/status
curl -i http://127.0.0.1:8800/health
curl http://127.0.0.1:8800/metrics
docker compose logs
```

These commands inspect service availability, readiness, metrics and logs. They are safe local checks when the service is part of the repository lab.

### Interpretation pattern

A good interpretation should connect the observed signal to a conclusion. For example: the status endpoint returned 200, Prometheus metrics exposed request counters, and logs confirmed the request was handled by the expected local service.

### Repository connection

This concept appears in Prometheus metrics labs, Grafana dashboard labs, capstone service, SIEM-style detection and final proof-of-work review.

### Safety note

Do not expose dashboards or metrics broadly unless intentional. Review logs, dashboard JSON and screenshots before publication.
